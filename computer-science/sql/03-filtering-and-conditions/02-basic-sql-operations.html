Additional Basic SQL Operations & Multiset Semantics

Having learned the basics of schema manipulation and the standard SELECT-FROM-WHERE block, it is time to complete your fundamental query toolkit. This module bridges the gap between basic data retrieval and complex, expressive relational queries.

Part 2 Basic SQL Operations

1. Module Context & Objectives

In earlier lessons, we introduced the basic structure of SQL (CREATE TABLE, schema manipulation, and standard querying). If you feel slightly uncomfortable at this stage, it is perfectly normal—it is the standard stage of language acquisition!

Objective: To finalize our understanding of the basic query structure by learning operations that make queries expressive and practical for real-world scenarios.

2. The Cartesian Product & Joins

The Cartesian Product is the primitive foundational operation in SQL for combining data. By definition, it generates all combinations of tuples (rows) from two relations (tables).

The Mechanism

SELECT * FROM instructor, teaches;
  • The result contains attributes (columns) of both tables.
  • Every single instructor row is paired with every single teaches row.

⚠️ The Problem

Executing a raw Cartesian product produces an explosion of rows, many of which are completely meaningless (e.g., pairing an instructor with a course they don't actually teach).

The Solution: Join via WHERE Condition

To filter out meaningless combinations, we apply a WHERE condition. This acts conceptually as an Equi-join or provides Natural Join behavior. 

SELECT name, course_id 
FROM instructor, teaches 
WHERE instructor.ID = teaches.ID;

💡 Deep Insight (Important):

The Cartesian product is the primitive operation in relational algebra. Conceptually, every SQL join happens in this order:

Cartesian Product → Selection (Filtering) → Projection (Choosing Columns)

This is pure relational algebra thinking applied to SQL!

3. The Rename Operation (AS) & Self Joins

The Rename operation is where the real power of relational databases shines, particularly when dealing with hierarchies.

Why do we need to Rename?

  • Attribute ambiguity: Resolving conflicts when two tables have identical column names.
  • Self-joins: When the exact same table needs to appear multiple times in the FROM clause. You cannot compare rows within the same table without creating logical copies.

Example: Self Join

Find instructors earning more than some Computer Science instructor.

SELECT DISTINCT T.name 
FROM instructor AS T, instructor AS S 
WHERE T.salary > S.salary 
AND S.dept_name = 'Comp. Sci.';

Key Concept: AS creates logical copies of a relation in memory during query execution. Note that the keyword AS is optional (e.g., writing instructor T is perfectly valid).

4. String Operations — Pattern Matching (LIKE)

The LIKE operator acts as a primitive text search operator before implementing heavy full-text indexing solutions.

Pattern Matching Symbols

Symbol Meaning
% Matches any substring (including an empty string).
_ Matches exactly one character.

Example: Search by Substring

SELECT name 
FROM instructor 
WHERE name LIKE '%dar%';

Matches names like: Darwin, Majumdar, Sardar.

Important Rules:

  • String comparisons are typically case-sensitive.
  • Escaping Characters: Used when the character % or _ is meant to be read as a literal string.
    Example: LIKE '100\%' ESCAPE '\'

5. Formatting Output: ORDER BY Clause

The ORDER BY clause is used to sort the output of your query.

  • Default: Ascending order (ASC).
  • Descending: Requires the DESC keyword.
  • Multi-attribute sorting: Sorting occurs lexicographically. (e.g., sort by department first, then by name within that department).
SELECT DISTINCT name 
FROM instructor 
ORDER BY dept_name, name DESC;

6. Limiting Output Size

Limiting results is crucial for performance, database pagination, and user interfaces. Very large result sets must be paginated. Syntax for limiting results varies significantly depending on your specific DBMS.

DBMS Syntax Used
Oracle / PostgreSQL (Standard SQL) FETCH FIRST n ROWS ONLY
MySQL / PostgreSQL LIMIT n
SQL Server TOP n

Example (Standard SQL Form):

SELECT DISTINCT name 
FROM instructor 
ORDER BY name 
FETCH FIRST 10 ROWS ONLY;

7. Advanced WHERE Clause Predicates

To write more expressive queries, SQL provides advanced conditional predicates:

  1. Range — BETWEEN:
    WHERE salary BETWEEN 90000 AND 100000;
    Equivalent to: salary >= 90000 AND salary <= 100000
  2. Tuple Comparison:
    WHERE (instructor.ID, dept_name) = (teaches.ID, 'Biology');
    More compact multi-condition equality check.
  3. Set Membership — IN:
    WHERE dept_name IN ('Comp. Sci.', 'Biology');
    Equivalent to writing multiple OR conditions.

8. Duplicates & Multiset Semantics

To deeply understand database behavior, you must understand how SQL handles data collections under the hood. We must differentiate between standard Set Theory (from Relational Algebra) and how SQL actually operates.

The Key Difference

  • Relational Algebra: Operates strictly on Set semantics. A mathematical set cannot contain duplicate elements.
  • SQL: Operates on Multiset (bag) semantics. SQL inherently allows duplicates.

Multiset Behavior Rule

If a specific tuple appears c times in a relation:

  • Selection: Retains all c copies.
  • Projection: May create even more duplicates by dropping distinguishing columns.
  • Cartesian Product: Multiplies duplicates across relations.

The Important Conceptual Formula

Consider this SQL query structure:

SELECT A1, A2 FROM r1, r2 WHERE P

This query is mathematically equivalent to the following Relational Algebra expression:

$$ \Pi_{A1,\, A2}\bigl(\,\sigma_{P}(r_1 \times r_2)\,\bigr) $$
This formula represents a Projection ( Π ) applied on top of a Selection ( σ ) applied on top of a Cartesian Product ( × ) of two relations — often abbreviated as: "Projection of a Selection on a Cartesian Product."

⚠️ Note: This entire operation is evaluated using multiset (bag) semantics — meaning duplicate rows are preserved in the output, just like standard SQL behavior (unless you use SELECT DISTINCT).

Final Conceptual Takeaway

Everything you do with basic SQL data retrieval boils down to mastering these five primitive steps in sequence:

  1. Cartesian Product (Combining datasets)
  2. Selection (Filtering rows)
  3. Projection (Selecting specific columns)
  4. Ordering (Sorting the output)
  5. Renaming (Resolving logic and ambiguity)
