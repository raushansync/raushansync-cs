Intermediate SQL — Joins & Views

This module has two major topics: Join Expressions and Views. I'll teach each concept clearly, and you can consolidate everything later in the practical lab.

4.2 Joins & Views

Part 1: Join Expressions

What is a Join?

A join takes two relations and produces one result relation by combining their tuples. Under the hood, every join is essentially a Cartesian product with conditions applied on top. Joins are most commonly used as subquery expressions inside the FROM clause.

Setting Up the Example

We will use two small tables throughout this tutorial to demonstrate the concepts. Keep this picture in your head:

Table: product

prod_id name category price
ELEC-10 Laptop Electronics 1200
FURN-20 Desk Furniture 300
TOY-30 Action Figure Toys 25

Table: supplier_link

prod_id supplier_id
ELEC-10 SUP-01
FURN-20 SUP-02
ELEC-99 SUP-03

Notice the deliberate information gaps:

  • TOY-30 exists in product but has no entry in supplier_link (its supplier is unknown).
  • ELEC-99 exists in supplier_link but has no entry in product (its product details are unknown).

These gaps are the key to understanding why different join types exist.

Type 1: Cross Join

The simplest join — it's just a Cartesian product. Every row from table A is matched with every row from table B.

-- Explicit
SELECT * FROM product CROSS JOIN supplier_link;

-- Implicit (same result)
SELECT * FROM product, supplier_link;

If product has m rows and supplier_link has n rows, you get m × n rows. This is mostly a building block — you'll rarely use it directly.

Type 2: Inner Join

This is the most restrictive join. It returns only those tuples that have a match in both tables.

SELECT * FROM product INNER JOIN supplier_link ON product.prod_id = supplier_link.prod_id;

Result: only ELEC-10 and FURN-20 appear — they exist in both tables. TOY-30 (no supplier) and ELEC-99 (no product details) are both dropped. Think of it as the intersection of the two sets.

The NATURAL Keyword

When you write NATURAL INNER JOIN, SQL automatically joins on all columns that share the same name, and crucially, it removes the duplicate column from the result. Without NATURAL, you'd see prod_id appear twice.

-- Without NATURAL: two prod_id columns appear
SELECT * FROM product INNER JOIN supplier_link ON product.prod_id = supplier_link.prod_id;

-- With NATURAL: only one prod_id column appears
SELECT * FROM product NATURAL INNER JOIN supplier_link;

Type 3: Outer Joins

Outer joins are an extension of inner join designed to avoid losing information. They include unmatched tuples from one or both tables, filling in NULL for the missing attributes.

Left Outer Join

Keeps all rows from the left table. If a left-table row has no match in the right table, the right-table columns are filled with NULL.

SELECT * FROM product NATURAL LEFT OUTER JOIN supplier_link;
prod_id name category price supplier_id
ELEC-10 Laptop Electronics 1200 SUP-01
FURN-20 Desk Furniture 300 SUP-02
TOY-30 Action Figure Toys 25 null

TOY-30 is preserved (it's in the left table) with NULL for supplier_id. ELEC-99 is still gone (it's only in the right table).

Right Outer Join

Keeps all rows from the right table. Mirror image of left outer join.

SELECT * FROM product NATURAL RIGHT OUTER JOIN supplier_link;
prod_id name category price supplier_id
ELEC-10 Laptop Electronics 1200 SUP-01
FURN-20 Desk Furniture 300 SUP-02
ELEC-99 null null null SUP-03

ELEC-99 is now preserved with NULLs for all product details. TOY-30 is gone.

Full Outer Join

Keeps all rows from both tables. It's the union of left and right outer joins.

SELECT * FROM product NATURAL FULL OUTER JOIN supplier_link;
prod_id name category price supplier_id
ELEC-10 Laptop Electronics 1200 SUP-01
FURN-20 Desk Furniture 300 SUP-02
TOY-30 Action Figure Toys 25 null
ELEC-99 null null null SUP-03

No information is lost. Every row from both tables appears.

Join Conditions: ON vs USING vs NATURAL

You have three ways to specify how to join two tables:

Syntax What it does
NATURAL Automatically joins on all same-named columns; removes duplicate column
ON <predicate> You specify the condition explicitly; duplicate columns are kept
USING (col) Join on specific named columns; removes the duplicate column 
-- ON: keeps two prod_id columns
product INNER JOIN supplier_link ON product.prod_id = supplier_link.prod_id

-- USING: keeps only one prod_id column
product FULL OUTER JOIN supplier_link USING (prod_id)

Why Joins Are Expensive

A join computes a Cartesian product first. If both tables have 1 million rows, the intermediate product is $10^{12}$ rows — even if your final result is just 10,000 rows. This is why database systems invest heavily in smart join algorithms (which you'll study later).

Part 2: Views

The Motivation

A database has a logical model — all the actual tables. But you often don't want every user to see everything. For example, staff handling inventory shouldn't see executive salaries. Views solve this.

A view is a virtual relation — it looks and behaves like a table, but it has no physical storage. It's defined by a query expression, and that expression is re-evaluated every time someone queries the view.

Creating a View

CREATE VIEW v AS <query expression>;

Example — hide salary from staff table:

CREATE VIEW staff_public AS
    SELECT staff_id, name, division
    FROM staff;

Now staff_public behaves exactly like a table with three columns. The salary column doesn't just have its values hidden — it doesn't even appear to exist.

You query a view just like a real table:

SELECT name
FROM staff_public
WHERE division = 'IT';

What actually happens internally: the system substitutes the view definition and executes:

SELECT name
FROM (SELECT staff_id, name, division FROM staff)
WHERE division = 'IT';

Views with Computed Data

Views can contain aggregations and computed columns that don't exist in any real table:

CREATE VIEW division_total_salary(division, total_salary) AS
    SELECT division, SUM(salary)
    FROM staff
    GROUP BY division;

No physical table stores total_salary — it's computed fresh each time you query this view.

Views Defined Using Other Views

A view can reference another view. This is called view dependency.

CREATE VIEW it_staff_2024 AS
    SELECT s.staff_id, s.name, a.project_id
    FROM staff s, assignments a
    WHERE s.staff_id = a.staff_id 
      AND s.division = 'IT'
      AND a.year = '2024';

CREATE VIEW it_staff_2024_hq AS
    SELECT staff_id, name
    FROM it_staff_2024
    WHERE location = 'HQ';

it_staff_2024_hq depends directly on it_staff_2024.

View Expansion

When you query it_staff_2024_hq, the system expands it by substituting the definition of it_staff_2024 inside it, producing one big nested query against real tables. This process repeats until no views remain — that's view expansion.

The rule: this expansion terminates as long as no view is recursive (i.e., no view references itself, even indirectly).

Updating Views

Since views are virtual, any INSERT, UPDATE, or DELETE on a view must be translated into an operation on the underlying real table.

Simple case (works): Inserting into staff_public:

INSERT INTO staff_public VALUES ('S-101', 'Alice', 'Sales');

This becomes an insert into staff with salary = NULL — as long as salary is nullable, this works.

Ambiguous case (fails): Consider a view joining two tables:

CREATE VIEW staff_division_info AS
    SELECT staff.staff_id, staff.name, division.building
    FROM staff, division
    WHERE staff.division = division.div_name;

INSERT INTO staff_division_info VALUES ('S-202', 'Bob', 'Tower A');

Which division do you assign if 'Tower A' houses multiple divisions? What if Bob has no division? There's no unique translation — so this update is rejected.

Contradictory case (impossible):

CREATE VIEW hr_staff AS
    SELECT * FROM staff WHERE division = 'HR';

INSERT INTO hr_staff VALUES ('S-303', 'Charlie', 'Marketing', 60000);

If this succeeded, the new tuple (division = 'Marketing') would immediately disappear from the view since it doesn't satisfy division = 'HR'. This is contradictory, so most systems reject it.

General rule: Most SQL systems allow updates only on simple views — views that reference exactly one table, have no aggregates, no GROUP BY, no DISTINCT, and no expressions in the SELECT clause.

Materialized Views

Sometimes you want the performance benefit of a real table but the logical convenience of a view. A materialized view is a view whose result is physically stored as a table.

The trade-off: if the underlying tables change, the materialized view becomes stale and needs to be refreshed. You're trading storage and maintenance overhead for faster query performance.

Summary of Joins & Views

Concept Description
CROSS JOIN Cartesian product; all combinations.
INNER JOIN Intersection; keeps only rows that match the condition in both tables.
LEFT OUTER JOIN Keeps all left-table rows, fills missing right-table data with NULL.
RIGHT OUTER JOIN Keeps all right-table rows, fills missing left-table data with NULL.
FULL OUTER JOIN Keeps all rows from both tables, filling with NULL where matches fail.
NATURAL vs ON NATURAL drops duplicate columns automatically; ON keeps them.
Virtual View A saved query behaving as a table; evaluated dynamically. No physical storage.
Updatable Views Usually restricted to "simple views" spanning a single table without aggregation.
Materialized View Physically stored view results. Faster querying, but requires refreshing to avoid stale data.
