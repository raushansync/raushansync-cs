Transition from the conceptual to the practical. Learn the mathematical foundations of relational databases, how to design tables with constraints, and the syntax to create, populate, and query your data.

1. The Anatomy of a Relation

In a Relational Database Management System (RDBMS), data isn't just thrown into files; it is meticulously organized into formal mathematical structures. Here is the terminology you need to know:

  • Relation: The formal mathematical term for a table.
  • Attributes: The columns of the table. They represent the properties of the entity you are modeling (e.g., Roll_Number, First_Name, Date_of_Birth). The order of columns does not matter to the database, but their names absolutely do.
  • Tuples: The rows of the table. Each tuple represents a single, unique record.
  • Uniqueness: A relation is fundamentally a mathematical set. Because sets cannot contain duplicate elements, every tuple in a relation must be entirely distinct from every other tuple. Like columns, the order of tuples does not matter.

Translation Guide

Academics and software engineers use slightly different words for the exact same things:

  • Relation = Table
  • Attribute = Column = Field
  • Tuple = Row = Record

2. Attributes, Domains, Schema, and Instance

Attributes and Domains

When designing a database, you only select attributes relevant to your business needs. A critical rule of relational design is that an attribute must be atomic, meaning it is indivisible.

Example: You should not have a single attribute called Full_Name if your application frequently needs to sort by Last_Name. Break it into atomic parts: First_Name and Last_Name.

Every attribute is tied to a Domain. A domain is the universal set of permitted values for that specific column.

  • Data Types: Domains enforce data types. A Date_of_Birth domain will reject a simple text string like "March 27th"; it demands a proper date format.
  • Nullability: Some attributes are optional. If a student does not have a passport, you cannot leave the field "blank" in a way that implies an empty string. Instead, you use a special marker called NULL. NULL signifies that the value is unknown or does not exist. Mandatory fields (like Roll_Number) cannot be NULL.

Schema vs. Instance

These two terms separate the structure of the database from the actual data it holds at any given second.

Concept Definition Mathematical Representation
Schema
(The Blueprint)		 Defines the logical structure of the relation: its name, its attributes, and the domains of those attributes. It rarely changes. If you have $n$ attributes, the relational schema is defined as:

$R(A_1, A_2, ..., A_n)$
Instance
(The Data Snapshot)		 The actual set of data rows present in the table at a specific moment in time. It changes constantly as data is added, removed, or updated. If we have domains $D_1, D_2, ..., D_n$ for our attributes, an instance $r$ is a subset of the Cartesian product of those domains:

$r \subseteq D_1 \times D_2 \times ... \times D_n$

Every individual tuple $t$ is written as $t = (a_1, a_2, ..., a_n)$ where each $a_i \in D_i$.

3. Database Keys

Because every tuple in a relation must be unique (remember our set theory rule), we need a reliable way to identify them. We use Keys to achieve this.

SK
Super Key

Any combination of attributes that uniquely identifies a row. For a student, Roll_Number is a super key. The combination of Roll_Number + First_Name is also a super key.

CK
Candidate Key

A minimal super key. It uniquely identifies a row, but if you remove any single attribute from it, it loses that unique identifying power. Roll_Number is a candidate key. Roll_Number + First_Name is not.

PK
Primary Key

The specific candidate key chosen by the database designer to identify records. You might have multiple candidate keys (e.g., Roll Number and Aadhaar Number), but you only pick one as the PK.

FK
Foreign Key

An attribute in one table that points to the primary key of another table. This is how relationships between tables are formed and referential integrity is maintained.

What is a Surrogate Key?

Sometimes, natural data isn't easily distinguishable. For example, you might place three identical orders on an e-commerce site at the exact same time. The natural data is the same. To fix this, systems generate a Surrogate Key—a synthetically generated identifier (like an Order_ID or an auto-incrementing integer) purely to tell rows apart.

4. Relational Query Languages

Once your data is structured, you need a way to ask questions about it (querying). There are two main paradigms in programming:

Paradigm Focus Example
Procedural Tells the system how to get the result step-by-step. Writing a loop in C to iteratively guess a number, check the deviation, refine the guess to compute a square root, and manage memory.
Declarative Tells the system what result you want, leaving the underlying execution up to the system. Stating you want a value $m$ such that $m^2 = n$.

Relational databases utilize declarative mathematical models (like Relational Algebra and Relational Calculus) to fetch data efficiently without the user writing complex loops or memory management steps. SQL is a declarative language.

5. SQL Categories: DDL & DML

SQL commands are broadly categorized based on what they manipulate: the structure (Schema) or the actual data (Instance).

Data Definition Language (DDL)

DDL is used to define and modify the structure of database objects.

  • CREATE — create a new table or database
  • DROP — delete a table or database
  • ALTER — modify an existing table's structure (e.g., add a column)

Data Manipulation Language (DML)

DML is used to manipulate the actual data inside the tables.

  • INSERT — add new tuples (rows)
  • UPDATE — modify existing tuples
  • DELETE — remove tuples
  • SELECT — retrieve data (often categorized as DQL - Data Query Language, but frequently grouped with DML)

6. Creating and Dropping Tables

Table Creation Syntax

You use the CREATE TABLE command, specifying the table name, column names, their data types, and any constraints.

CREATE TABLE table_name (
    attribute1 datatype [constraints],
    attribute2 datatype,
    ...
);

Example: Creating an Instructor Table

CREATE TABLE instructor (
    id CHAR(5) PRIMARY KEY,
    name VARCHAR(20) NOT NULL,
    dept_name VARCHAR(20),
    salary NUMERIC(8, 2)
);

SQL Constraints

Constraints restrict attribute values to enforce data integrity.

  • NOT NULL: The attribute must have a value.
  • UNIQUE: All values in this column must be distinct across all rows.
  • PRIMARY KEY: Uniquely identifies the row. Inherently acts as both NOT NULL and UNIQUE.
  • FOREIGN KEY (col_name) REFERENCES other_table(col_name): Maintains referential integrity between tables. Only values existing in the referenced table can be inserted.

The Dependency Rule (Very Important)

If Table A has a foreign key pointing to Table B, Table B must be created first. You cannot reference a table that does not exist yet! Similarly, when dropping tables, you must drop Table A before you can drop Table B.

Dropping a Table

Deletes the table structure and all data inside it permanently.

DROP TABLE instructor;

7. Inserting Data (DML)

To populate your newly created schema with instances (data), use the INSERT INTO command.

INSERT INTO instructor 
VALUES ('1001', 'Rahul', 'CS', 90000);

Note: Values must strictly follow the attribute order defined during table creation unless columns are explicitly specified.

8. Basic SQL Query Structure

The most fundamental way to retrieve data is the SELECT statement.

SELECT attributes    -- Projection (What columns do you want?)
FROM table_name      
WHERE condition;     -- Selection (What rows do you want?)

The SELECT Clause

  • Select all columns: Use the asterisk * wildcard.
    SELECT * FROM instructor;
  • Select specific columns: List them separated by commas.
    SELECT name, salary FROM instructor;
  • Remove duplicates: Use the DISTINCT keyword.
    SELECT DISTINCT dept_name FROM instructor;
  • Literals: You can select constants. This produces a constant output column.
    SELECT 437 AS value;
  • Arithmetic: SQL supports computations directly inside the SELECT clause.
    SELECT name, salary/12 AS monthly_salary FROM instructor;
    (Note: Renaming output using AS affects only the query result, not the original table schema).

9. The WHERE Clause & Cartesian Product

The WHERE clause is used for filtering rows based on specific conditions.

SELECT name 
FROM instructor 
WHERE dept_name = 'CS';

Logical Operators

You can combine multiple conditions using AND, OR, and NOT.

SELECT name, salary 
FROM instructor 
WHERE dept_name = 'CS' AND salary > 80000;

Cartesian Product (FROM with multiple tables)

If you specify multiple tables in the FROM clause without a proper join condition, SQL produces a cross product.

SELECT * FROM instructor, teaches;

If the instructor table has $m$ rows and the teaches table has $n$ rows, the result will have $m \times n$ rows. This is computationally expensive and usually not what you want unless deliberately paired with a WHERE clause to map the keys.

Key Conceptual Takeaways

  • Tables represent relations: They are mathematical sets of unique tuples.
  • Schema vs. Instance: The schema is the blueprint; the instance is the actual data at a moment in time.
  • Keys identify data: Super, Candidate, Primary, and Foreign keys form the backbone of relational logic.
  • Constraints enforce data integrity: Rules like NOT NULL and UNIQUE prevent bad data from entering your system.
  • SQL is Declarative: You use DDL (CREATE, DROP) to build structures, and DML (INSERT, SELECT) to interact with the data, telling the engine what to do, not how.
  • Foreign keys enforce dependency: Always create referenced tables first, and drop them last.
