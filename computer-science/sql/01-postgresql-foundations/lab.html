Lab: Getting Comfortable with psql

It's time to test your setup. In this lab, you will open your terminal, connect to PostgreSQL, execute basic meta-commands, intentionally cause some errors to understand how the parser responds, and build your isolated practice environment.

Practical Lab PostgreSQL Foundations

Step 1: Connecting to PostgreSQL

Open your terminal (macOS/Linux) or Command Prompt/SQL Shell (Windows). Start by checking if your server is reachable. 

# Check your installed version
psql --version

# Connect using default superuser
psql -U postgres -d postgres

If this fails, make sure you are using the password you set during PostgreSQL installation.

Note: PostgreSQL username is NOT your system username.

Expected Output

You should see a welcome message and a prompt that looks like this:

psql (16.x)
Type "help" for help.

postgres=#

Note: You may see additional warnings (especially on Windows). This is normal and can be ignored if you see the `postgres=#` prompt.

Step 2: Exploring the Server

Now that you are inside the `psql` interface, you are no longer typing Bash/Zsh or Windows commands. You are communicating directly with PostgreSQL. Let's use meta-commands (the ones starting with \) to look around. 

-- 1. List all databases on this server
\l

-- 2. Check the current connection details
\conninfo

-- 3. List all users (roles)
\du

Step 3: Creating Your Sandbox Database

We do not want to practice in the system `postgres` database. Let's create our own container to keep things organised. 

-- Create a new database. Don't forget the semicolon!
CREATE DATABASE learning_sql;

-- Switch your connection to the new database
\c learning_sql

Look closely at your prompt. It should have changed from postgres=# to learning_sql=#. This confirms you are in the right place! 

-- Verify that it is completely empty
\dt

Output should say: "Did not find any relations/tables."

Step 4: Using PostgreSQL as a Calculator

Let's test the query parser and see data types in action. Type the following SQL commands. Notice how Postgres treats integers vs. decimal numbers. 

-- Basic arithmetic
SELECT 10 + 5;

-- Integer division (Wait, what is 10 divided by 3?)
SELECT 10 / 3;

Why did 10 / 3 output 3?

Because both 10 and 3 are integers. Postgres strictly maintains the data type and performs integer division (truncating the decimal).

Now try it with decimals to see the difference:

-- Decimal division
SELECT 10.0 / 3.0;

Step 5: How to Get Unstuck

Everyone makes typos. Let's intentionally trigger common errors so you know exactly how to handle them when they happen by accident.

The Forgotten Semicolon Trap

Type this exact line and press Enter (notice there is NO semicolon):

SELECT 100

Nothing happens! But look at the prompt. It changed from =# to -#. Postgres thinks you are just continuing on a new line. To fix it, just type a semicolon and press Enter. 

;

The Misspelled Command Trap

Let's misspell a SQL keyword to see how the Parser complains.

SELCT 500;

Output: ERROR: syntax error at or near "SELCT"
Whenever you see "syntax error at or near", it means step 1 of the query pipeline (The Parser) failed. Check your spelling!

The Runaway Quote Trap

Type this and press Enter:

SELECT 'Raushan

Now the prompt changed to '#. psql thinks you are typing a multi-line text string and is waiting for the closing quote.

How to abort: Press Ctrl + C. This usually cancels the current input and returns you to the postgres=# prompt.

Note: On some systems (especially Windows), Ctrl + C may exit psql completely. If that happens, simply reconnect using: psql -U postgres -d postgres
