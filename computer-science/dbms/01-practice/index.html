Section C — Assertion & Reason

Instructions for this section: Each question contains an Assertion (A) and a Reason (R). Choose the option that correctly describes the truth of both statements and their relationship.

A — Both Assertion and Reason are true, and Reason is the correct explanation of Assertion.
B — Both Assertion and Reason are true, but Reason does not correctly explain Assertion.

13 ASSERTION – REASON

Assertion (A): In a file-based system, concurrency anomalies can occur even when only two users are simultaneously accessing the data.

Reason (R): Concurrency anomalies arise whenever two or more operations access shared mutable data simultaneously without coordination — the total number of users in the system is irrelevant to whether the anomaly occurs.

14 ASSERTION – REASON

Assertion (A): If every application that accesses a shared file uniformly enforces the same integrity constraints in its own code, this is functionally equivalent to a DBMS enforcing those constraints at the storage level.

Reason (R): A DBMS enforces constraints at the storage level, making them uniformly applied regardless of which application accesses the data — no application can bypass them, and no developer can forget to implement them.

15 ASSERTION – REASON

Assertion (A): Atomicity in DBMS transaction management ensures that each transaction is small in scope and executes instantaneously — it refers to operations that happen in a single, fast step.

Reason (R): Atomicity means indivisible — a transaction may involve thousands of records and take considerable time, but it must either commit entirely or roll back entirely; size and execution speed are irrelevant to whether a transaction is atomic.

After This Practice

If any question surprised you, return to the notes and re-read that section from scratch. The questions above target the most persistent misconceptions in DBMS fundamentals — particularly the redundancy–inconsistency chain, atomicity as indivisibility not speed, the unreliability of code-level constraint enforcement, and the meaning of "kind, not degree."

  • Redundancy's real danger is inconsistency — conflicting truths, not wasted bytes.
  • Partial execution is worse than complete failure — it is silently wrong, not visibly failed.
  • A constraint in application code has exactly one enforcer: the developer who wrote it. Anyone else can bypass it.
  • Atomic means indivisible — a transaction spanning 10,000 rows is still atomic if it commits or rolls back as one unit.
  • Concurrency anomalies are structural, not scale-dependent — two users and shared mutable state is enough.
  • A DBMS is an engineering contract. Every feature is one clause of that contract, answering one specific failure mode.
If a DBMS enforces constraints, manages concurrent access, and guarantees atomicity — all transparently, without the application asking —
then what exactly does the application developer's responsibility begin and end with?
