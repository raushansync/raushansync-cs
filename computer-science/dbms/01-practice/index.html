After This Practice

If any question surprised you, review the underlying idea and try to explain it with a new example. The questions above target the most persistent misconceptions in DBMS fundamentals — particularly the redundancy–inconsistency chain, atomicity as indivisibility not speed, the unreliability of code-level constraint enforcement, and the meaning of "kind, not degree."

  • Redundancy's real danger is inconsistency — conflicting truths, not wasted bytes.
  • Partial execution is worse than complete failure — it is silently wrong, not visibly failed.
  • A constraint in application code has exactly one enforcer: the developer who wrote it. Anyone else can bypass it.
  • Atomic means indivisible — a transaction spanning 10,000 rows is still atomic if it commits or rolls back as one unit.
  • Concurrency anomalies are structural, not scale-dependent — two users and shared mutable state is enough.
  • A DBMS is an engineering contract. Every feature is one clause of that contract, answering one specific failure mode.
If a DBMS enforces constraints, manages concurrent access, and guarantees atomicity — all transparently, without the application asking —
then what exactly does the application developer's responsibility begin and end with?
