Section C — Assertion & Reason

Instructions for this section: Each question contains an Assertion (A) and a Reason (R). Choose the option that correctly describes the truth of both statements and their relationship.

A — Both Assertion and Reason are true, and Reason is the correct explanation of Assertion.
B — Both Assertion and Reason are true, but Reason does not correctly explain Assertion.
C — Assertion is true, Reason is false.
D — Assertion is false, Reason is true.

14 ASSERTION – REASON

Assertion (A): A DBA can change the physical storage structure of a table — such as switching from a heap file to a hash-organised file — without requiring any application code to be rewritten.

Reason (R): The three-level abstraction architecture enforces a strict separation between the physical and logical levels, so changes at the physical level are invisible to the logical and view levels above it.

15 ASSERTION – REASON

Assertion (A): SQL is a Turing Complete language, meaning it can express any computational logic that a general-purpose programming language can, and therefore does not need to be embedded inside another language.

Reason (R): SQL is designed as a specialised data retrieval and manipulation language, and in real applications it is typically embedded inside a host language like Python or Java that handles the application logic SQL cannot express.

16 ASSERTION – REASON

Assertion (A): The schema of a database changes far less frequently than the instance — data is inserted, updated, and deleted routinely, while the structural definition of tables and columns remains stable.

Reason (R): The schema is stored in the same physical disk blocks as the actual data rows, so changing it is inherently a more expensive and disruptive operation than changing instance data.

17 ASSERTION – REASON

Assertion (A): A poorly designed table that stores department-level information (like building and budget) together with instructor-level information in the same row is vulnerable to update anomalies when department details change.

Reason (R): Because the same department fact — such as its building name — is repeated across multiple rows, a real-world change to that fact requires updating every row that contains it; missing even one row leaves conflicting values in the database.

After This Practice

If any question surprised you, return to the concept and ask what failure mode it is designed to prevent. Every architectural decision in a DBMS exists to eliminate a specific class of problem. The questions above target the most persistent conceptual confusions in this chapter — particularly the difference between schema and instance, why physical changes don't break logical code, what DDL actually does versus DML, and why redundancy is a design failure rather than just inefficiency.

  • The three abstraction levels each serve a different stakeholder — physical for storage engineers, logical for developers, view for end users. Each level is protected from the complexity of the others.
  • Schema is structure; instance is content. The schema outlives any particular dataset. Instances change constantly; schemas change deliberately.
  • Physical Data Independence is not magic — it works because the abstraction stack enforces strict layer boundaries. Physical changes stay at the physical level.
  • DDL builds the container; DML operates inside it. CREATE TABLE defines structure (DDL); INSERT / SELECT / UPDATE / DELETE operate on data (DML). These are fundamentally different categories.
  • The Data Dictionary is the DBMS's own memory — it records every table and column that exists, and is checked before every query is processed.
  • Redundancy is a design failure, not a storage concern. Storing the same fact in multiple rows creates update anomalies, insertion anomalies, and deletion anomalies. Decomposition eliminates these by ensuring each fact lives in exactly one place.
  • The three-engine architecture separates concerns for a reason — Storage, Query, and Transaction management require different expertise and can be improved independently.
  • ACID is a four-part guarantee — each letter addresses a different class of failure. Confusing Atomicity with Isolation, or Durability with Consistency, is a common mistake worth correcting clearly.
  • SQL is not Turing Complete — it is designed to manipulate data, not to express general computation. Host languages handle the application logic.
A well-designed DBMS is a system of enforced separations —
each one eliminating a class of failure. If you understand what failure
each separation prevents, you understand why the system is built the way it is.
