1.3 DBMS Concepts & Architecture — Abstraction to Engine Internals

This section moves from the why of DBMS (covered in 1.2) to the what and how. You will learn how a DBMS hides complexity through three levels of abstraction, how it separates structure from data, how designers interact with it through two distinct languages, and why getting the data design wrong produces failures that cascade through the entire system. The section concludes by cracking open the database "black box" — revealing the three internal engines that make a DBMS work — and tracing how deployment architectures evolved from a single mainframe to today's cloud-distributed systems.

1. Big Picture Overview

This section is fundamentally about the idea of separation. Every major concept here — abstraction layers (here abstraction means "hiding implementation details and showing only essential features"), schema vs instance, DDL vs DML, logical vs physical design, the engine's subsystems — is an instance of separating one concern from another. That separation is not cosmetic; it is the engineering principle that makes databases manageable, trustworthy, and scalable.

The three threads running through this section are: how a DBMS hides complexity (abstraction), how it organises data correctly (design), and how it delivers the right behaviour internally (the engine). Understanding each thread, and how they connect, is the goal.

The Design Lesson Underneath

Every concept in this section exists to solve a specific problem. Abstraction exists because different stakeholders need to think about data differently. Schema exists because structure must outlive individual data entries. The engine's subsystems exist because no single program could reliably manage storage, querying, and transactions simultaneously. Understanding what each concept is solving is more important than memorising what it is.

2. The Three Levels of Abstraction

A key feature of any well-designed DBMS is that it hides complexity from the user. Not all complexity — the right complexity for the right audience. It does this by viewing data at three distinct levels, each of which separates how data is stored from how data is used.

Think of it this way: an airline has three groups of people who all interact with the same flight data — engineers who design the storage systems, database designers who define what data exists and how it relates, and passengers who only care about their own booking. All three need access to "data," but radically different amounts of it, in radically different forms. The three abstraction levels exist to serve these three audiences without mixing their concerns.

👤
View Level — Highest Level

This is what a specific user actually sees. It does not expose the full database — it presents only the portion relevant to a given role or task. Sensitive fields (like an employee's Salary) can be hidden entirely. Computed fields can appear without existing in storage — for example, "Age" shown to the user derived on the fly from "Date of Birth" in the table. Crucially, the same underlying data can be exposed through multiple different views simultaneously — a payroll view, an HR view, and a manager view can all draw from the same table while showing completely different columns.

FOR USERS
🗂️
Logical Level — Middle Level

This is the level at which the structure of the database is defined: what data exists, what tables there are, what columns each table has, and how different tables relate to each other. A database designer working at this level says things like "an Instructor record has an ID, a Name, and a Salary." The logical level deliberately ignores the complex physical reality of bits and bytes — it lets the designer think in terms of meaningful concepts, not storage mechanisms.

FOR DESIGNERS
⚙️
Physical Level — Lowest Level

This is where the data actually lives. How it is encoded in binary, which disk sectors it occupies, what data structures (B-trees, hash tables, etc.) organise it for fast access — all of this is the concern of the physical level. It is the territory of system engineers, not of application developers or end users. Most people working with a database never need to know anything at this level.

FOR ENGINEERS

Why This Separation Is Not Just Convenience

The three levels are not just organisational tidiness. They represent a guarantee: changing something at one level does not automatically break the levels above it. A system engineer can reorganise how data is stored on disk — moving from one storage format to another — without the logical structure (tables and columns) changing at all. A database designer can add a new table without any user's existing view being disrupted. This independence is a structural property of the system, not a side effect.

3. Schema vs Instance

Every database has two things that must never be confused: its structure and its content. These are formally called the Schema and the Instance.

📐

Schema

THE BLUEPRINT
  • The logical structure of the database — the definition of what exists
  • Defines the names of tables and the columns within them
  • Example: Customer(Name, ID, AccountNo) — this is a schema declaration, not data
  • Analogous to declaring a variable type in code: int x; — you are defining what kind of thing will exist, not yet putting a value in it
  • Changes very rarely — usually only when the business or data model fundamentally changes
📦

Instance

THE CONTENT
  • The actual data stored in the database at a specific moment in time
  • The contents of the tables — the real records, numbers, names, and values
  • Analogous to assigning a value to a variable: x = 10; — the structure already exists; now something is in it
  • Changes constantly — every INSERT, UPDATE, and DELETE creates a new instance
  • The instance is always temporary; the schema is what persists as the stable frame

The analogy with programming is worth sitting with. When a programmer writes int x;, they are defining a named space that can hold an integer. They have not stored anything yet — the variable's type is like the schema. When they write x = 10;, they are filling that space with a value — analogous to the instance. The schema defines what kinds of data may exist; the instance is the data that actually exists right now.

Physical Data Independence — The Critical Consequence

The separation of schema from physical storage leads to an important guarantee called Physical Data Independence: the logical schema should not break just because the physical storage method changes.

🔗
Physical Data Independence

If a database is migrated from a traditional hard drive to a solid-state drive — or if the underlying file format changes — the logical layer remains intact. The tables, the columns, and the relationships between them are defined at the logical level, not the physical level. Queries and application code written against the logical schema continue to work without modification. The physical and logical levels are deliberately insulated from each other.

4. Data Models

A data model is a collection of tools used to describe data, how it relates to other data, and the constraints that govern it. It is the conceptual vocabulary for thinking about data. Different models make different trade-offs about what kinds of data relationships they can represent and how efficiently.

🗄️
DOMINANT — THIS COURSE

Relational Model

The industry standard for structured data. Organises data into Tables (called Relations), where each table has Rows (Records) and Columns (Attributes). Every fact about an entity lives in a row; every category of information is a column. Relationships between tables are expressed through shared key values, not physical pointers. This is the model this course focuses on entirely.

📊
DESIGN PHASE

Entity-Relationship (ER) Model

Used primarily as a design tool before building the database, not as the implemented structure. The ER model lets designers draw out the entities in a system (e.g., Students, Courses) and the relationships between them (e.g., "a Student enrolls in a Course") diagrammatically. Once design is complete, the ER diagram is translated into a relational schema.

🕸️
EMERGING / SPECIALISED

NoSQL / Graph Models

Emerging models designed for data that does not fit naturally into rows and columns — social graphs, video, images, or loosely structured documents (like Facebook's friend network). Although these models are gaining ground for specific use cases, the Relational model remains the industry standard for structured, transactional data.

5. Database Languages: DDL vs DML

To interact with a database, two fundamentally different kinds of operations are needed: building the structure, and working with the data inside it. These are handled by two distinct language types, both realised in modern systems through SQL.

DDL — Data Definition Language

DEFINES STRUCTURE · BUILDS THE CONTAINER
  • Purpose: Defines the schema — the structure of the database
  • Action: It builds the "container" into which data will eventually go — not the data itself
  • Scope: Operates at the logical level — tables, columns, data types, constraints
CREATE TABLE Instructor (ID, Name, Dept)

DML — Data Manipulation Language

MANIPULATES DATA · OPERATES INSIDE THE CONTAINER
  • Purpose: Manipulates the instance — the actual data stored
  • Action: Performs operations on the data inside an already-defined container
  • Scope: Works with rows — retrieving, inserting, changing, or removing them
SELECT — Query/Read INSERT — Add UPDATE — Change DELETE — Remove

The Data Dictionary — DDL's Hidden Output

📖
The Data Dictionary (System Catalogue)

Every time you run a DDL statement, the database does not just create the table — it also updates an internal record of what tables and columns now exist. This internal record is called the Data Dictionary (or System Catalogue). It is a special internal table that the DBMS itself maintains to keep track of its own structure. When you query a table, the DBMS first checks the Data Dictionary to confirm the table exists and verify the column names and types before it processes anything. It is the database's own metadata — data about the data.

An Important Boundary: What SQL Cannot Do Alone

SQL is not Turing Complete. This is a precise statement: there are categories of complex logical computation — like sophisticated mathematical simulations or multi-step conditional branching logic — that SQL cannot express or execute on its own. This is not a flaw; SQL is designed as a data retrieval and manipulation language, not a general-purpose programming language.

In real-world applications, SQL is therefore embedded inside a "Host Language" — Python, Java, or C++ — which handles the heavy application logic, while SQL handles precisely what it is optimised for: retrieving and manipulating data from the database. The two languages work together, each doing what it does best.

6. Database Design: Logical vs Physical

Design in a DBMS context happens in two distinct phases, corresponding to the two lower levels of the abstraction stack.

Physical Design

HOW DATA IS STORED ON DISK
  • Concerns how files are laid out, how B-Trees are structured, how disk pages are organised
  • Decides data structures like indexes and hash tables to ensure fast access
  • Usually decided once during initial system setup and rarely revisited
  • Invisible to application developers and users — handled by the system

Logical Design

WHAT TABLES EXIST AND HOW THEY RELATE
  • Deciding which tables to create, what columns they contain, and how they relate to each other
  • Driven by two kinds of decisions in tandem:
  • Business Decisions: What data does the organisation need to track? (e.g., "We need to track student grades")
  • CS Decisions: How should that data be structured efficiently? (e.g., "Should grades live in the Student table or a separate Course table?")

Logical design is where most of the intellectual work happens — and where most of the serious mistakes are made. It is the territory of this section's central case study: the redundancy problem.

7. The "Bad Design" Case Study: The Redundancy Problem

The most important design question this section raises is: what happens when you store related data in a single merged table instead of splitting it across two properly separated tables?

The Scenario

Imagine designing a database for a university. Two things need to be tracked: faculty members (their names and salaries), and departments (their buildings and budgets). The temptation is to store everything in one table:

⚠️ BAD DESIGN — MERGED TABLE (faculty_dept)
Faculty_Name Salary Dept_Name Building Budget
Sharma, A. ₹90,000 Computer Science Taylor Hall $2,000,000
Singh, R. ₹85,000 Computer Science Taylor Hall $2,000,000
Verma, K. ₹92,000 Computer Science Taylor Hall $2,000,000
… 7 more rows for Computer Science, all with the same Building and Budget …

Why This Is Dangerous

①
Storage Waste

The strings "Taylor Hall" and "$2,000,000" are stored ten separate times — once for each faculty member in the Computer Science department. This is not merely inefficient; it is structurally wrong. A fact about a department (its building and budget) is being stored as if it were a fact about each individual person. The data model is misrepresenting reality.

②
Update Anomaly — The Real Danger

When the Computer Science budget changes, the system must update the Budget column in all ten rows. Now consider what happens if the system successfully updates nine rows and then crashes before the tenth. The database is now in a corrupted state: nine faculty members have one budget figure and one has a different one. Both figures appear valid — there is no way to detect the inconsistency without external knowledge of what the correct value should be. The database has become untrustworthy.

The Solution: Decomposition

The fix is to split the merged table into two properly separated tables, each storing only the data that belongs to the entity it represents.

Faculty Table

Name Salary Dept_Name ↗

Stores only what is true about a person. The Dept_Name column is a link - foreign key (we will see this in detail in upcoming articles.) to the Department table — not a copy of the department's data.

Department Table

Dept_Name 🔑 Building Budget

Stores only what is true about a department. Now if the budget changes, exactly one row is updated. There is one source of truth — and it cannot become inconsistent with itself.

This is not merely a performance improvement. It is a correctness improvement. The decomposed design accurately represents the structure of reality: departments have budgets, not individual faculty members. When data design mirrors reality correctly, anomalies of the kind described above become structurally impossible.

8. Design Approaches: Two Formal Methods

The redundancy problem above is not solved by intuition — at scale, databases have hundreds of tables and thousands of columns. Two formal methods exist for systematically arriving at correct designs.

Entity-Relationship (ER) Model

DIAGRAMMATIC DESIGN TOOL
  • A diagrammatic method for mapping business requirements into a data model before any tables are created
  • Identifies the Entities in the problem domain (e.g., Students, Instructors, Courses) and the Relationships between them (e.g., "a Student enrolls in a Course")
  • Works at the conceptual level — before SQL or schema definitions are written
  • Produces a blueprint that is then translated into a relational schema

Normalization

MATHEMATICAL THEORY FROM THE 1970s
  • A formal, mathematical theory for systematically eliminating redundancy from a database schema
  • Defines a series of "Normal Forms" — rules a schema must satisfy to be considered redundancy-free at that level
  • Directly prevents the update anomalies described in the case study above
  • Not optional — it is the scientific basis on which correct data design rests

ER and Normalization Are Complementary

ER modelling is used at the beginning of design — it helps you identify what entities and relationships exist before you commit to any table structure. Normalization is applied to the resulting schema — it checks whether the tables you defined are correctly decomposed and refines them if not. They are not competing approaches; they are sequential phases of the same design discipline.

9. Beyond the Relational Model

While the relational model is the primary focus of this course, two extended forms are worth understanding at a conceptual level.

🧩

Object-Relational Model

An extension of the relational model that allows columns to contain complex objects rather than simple scalar values. In a standard relational table, a column holds a number or a string. In an object-relational system, a column could hold an entire "Student object" — a structured record with its own fields. This bridges relational and object-oriented data representation, though it adds complexity to the schema and query model.

📄

XML (Extensible Markup Language)

A hierarchical, tag-based format for representing structured data. Unlike relational tables which are flat and rectangular, XML can represent nested, tree-structured information. It is rarely used inside a database for processing, but it is the dominant standard for exporting and interchanging data between different systems. When two systems that do not share a database need to exchange records, XML is a common transport format.

10. The Database Engine — The "Black Box"

A DBMS is not a single program. It is an engine built from multiple specialised subsystems, each handling a different class of problem. Understanding this internal architecture explains how a DBMS provides the guarantees it advertises: fast queries, safe transactions, crash recovery. Three major subsystems do this work.

💾

Storage Manager

INTERFACE BETWEEN DB AND OS
  • The OS manages files at the lowest level; the Storage Manager sits above it
  • Its job: figure out how to store data efficiently within those OS-managed files
  • Implements indexing and hashing to ensure fast retrieval — so queries do not have to scan every row
  • Effectively translates between "what the database needs" and "what the file system can provide"
🔍

Query Processor

TURNS SQL INTO EXECUTION PLANS
  • Takes the high-level SQL written by a user and converts it into low-level instructions the machine can execute
  • This is a multi-stage pipeline — not a single operation
  • The result is an efficient execution plan tailored to the current state of the database
🔒

Transaction Manager

GUARANTEES ACID PROPERTIES
  • Ensures every transaction satisfies the ACID properties — no partial commits, no inconsistent states
  • Concurrency Control: When two users attempt the same operation simultaneously (e.g., booking the last available train seat at the exact same millisecond), the Transaction Manager serialises them so only one succeeds and the data remains consistent
  • Recovery: If the system crashes mid-transaction, the Transaction Manager rolls back the incomplete operation so the database returns to a valid, consistent state

Inside the Query Processor: A Four-Stage Pipeline

The Query Processor is worth examining in more detail because it illustrates how much work happens invisibly between writing a SQL statement and receiving a result.

1
Parsing — Syntax Check

The first step is purely about correctness of form: did the user write valid SQL? Misspelled keywords, missing parentheses, or invalid column references are caught here before any data access happens. Think of it as a grammar check on the query.

2
Translation — SQL → Relational Algebra

The parsed query is converted from SQL — a declarative, English-like language — into Relational Algebra, a formal mathematical language of set operations. This translation creates an internal representation that the system can reason about precisely. SQL says what you want; Relational Algebra says what operations produce it.

3
Optimization — The Brain of the Processor

The single most important step. The optimizer examines the algebraic representation and calculates the most efficient way to execute it. For a query that joins three tables, the optimizer asks: which table should be scanned first? Should the join be done using an index, or would a full scan be faster given the current data volume? Different execution orders can differ in performance by orders of magnitude — the optimizer picks the cheapest plan automatically.

4
Evaluation — Execution and Result Return

The chosen execution plan is finally run against the actual data. The storage manager is called to retrieve the required records. The results are assembled and returned to the user or application that issued the query.

11. ACID Properties — What the Transaction Manager Guarantees

The Transaction Manager's responsibility is to ensure that every database transaction satisfies four properties, collectively known as ACID. These are not aspirational goals — they are guarantees the DBMS is engineered to uphold.

A

Atomicity

A transaction either completes in full or has no effect at all. There is no in-between. If a bank transfer debits one account but the system crashes before crediting the other, the debit is rolled back. Partial transactions do not persist.

C

Consistency

The database must be in a valid state both before and after every transaction. Every rule and constraint defined in the schema must hold. A transaction that would violate a constraint (e.g., making a balance go negative) is not permitted to complete.

I

Isolation

Transactions executing concurrently must not interfere with each other. Each transaction behaves as if it has exclusive access to the data. This is what the Transaction Manager's concurrency control mechanism enforces.

D

Durability

Once a transaction has been committed, its effects are permanent. Even if the system crashes immediately after a commit, the change survives. This is enforced through techniques like write-ahead logging that persist changes to stable storage before acknowledging the commit.

Why All Four Must Hold Together

Each ACID property protects against a distinct class of failure. Atomicity protects against partial execution. Consistency protects against rule violations. Isolation protects against concurrent interference. Durability protects against data loss after commitment. A system that satisfies three of the four is not "mostly safe" — it has a structural vulnerability that can corrupt data under the right conditions. All four must hold simultaneously.

12. Architecture Evolution

How database systems are deployed has evolved in step with computing infrastructure. The same DBMS concepts — the three-level abstraction, ACID transactions, the query pipeline — have been implemented in three fundamentally different deployment architectures.

🖥️
Monolithic
Mainframe era
One machine does everything
🔗
Client–Server
Standard today
DB on server, app on client
☁️
Cloud / Distributed
AWS, Google Cloud
Spread across many machines

The Monolithic (Mainframe) era placed everything on a single large computer. The database, the application, and the user terminals all connected to one central machine. It was reliable but inflexible — a single point of failure and a hard ceiling on scale.

The Client–Server model separated concerns: the database lives on a dedicated server, and applications (a website, a desktop app) run on separate client machines that query the server over a network. This is still the dominant deployment model today. The network connection introduces latency but enables many clients to share the same database simultaneously.

The Cloud / Distributed architecture takes this further: the database itself is distributed across multiple machines, possibly in different geographic regions, managed by a cloud provider such as AWS or Google Cloud. This allows massive scalability and resilience — if one machine fails, others continue. It also introduces new challenges around keeping distributed copies of data consistent with each other, which is where the frontier of database research currently lives.

14. Common Misconceptions

❌
"The View Level just means a visual interface — like a dashboard or a form."

It is tempting to think "view" means a graphical display, because that is what "view" usually means in everyday language. In database terminology, a View is a defined, named window onto a subset of the database — constructed from a query — that can be presented to a user as if it were a table, even though it may not be stored as one. Multiple different views can exist simultaneously over the same underlying data. The view level is about data access control and data presentation — not about graphical interfaces.

✓ A View is a defined logical window over specific data — it controls what a user sees and can derive computed values, but it is not a GUI concept.
❌
"DDL and DML are two separate languages — you choose one or the other."

In modern practice, DDL and DML are both part of SQL. They are not competing languages or separate tools. They are classifications of what a particular SQL statement does: some SQL statements define structure (DDL), and others manipulate data (DML). A developer uses both in the same SQL session, in the same tool, against the same database. The distinction matters for understanding what each statement affects, not for choosing which language to use.

✓ DDL and DML are categories of SQL statements — both are expressed in SQL, used together in the same system.
❌
"A merged table is bad only because it wastes storage space."

Storage waste is a minor consequence. The catastrophic consequence is the update anomaly: the possibility of a partial update leaving the database in an internally inconsistent state with no way to detect which value is correct. A merged table with redundant data violates the principle of having a single source of truth. When that source is duplicated, inconsistency becomes a structural possibility — not just a risk to be managed carefully, but an architectural inevitability under failure conditions.

✓ The primary danger of a bad design is update anomalies — partial updates creating undetectable corruption — not storage cost.
❌
"The Query Optimizer is just about making things faster."

While the optimizer does produce faster execution, framing it purely as a performance tool misses its significance. The optimizer is what makes SQL practical at all. SQL is declarative: you state what result you want, not how to compute it. The optimizer is the component that bridges this gap — it determines the how. Without the optimizer, users would have to write procedural query plans manually for every query, which would defeat the purpose of a high-level query language.

✓ The optimizer is what makes declarative SQL viable — it translates intent into efficient execution, not just making existing plans faster.

15. Concept Checkpoints

These questions test reasoning, not recall. Work through each one to verify that you understand the logic — not just the labels.

Q1

The three abstraction levels are designed so that changes at one level do not propagate upward and break the levels above it. Describe a specific scenario where this independence fails — that is, where a change at the physical level would force a change at the logical or view level. What architectural property has been violated, and what does this tell you about the conditions under which physical data independence holds?

Q2

Schema changes very rarely; instances change constantly. Given this, what would happen to a running application if the schema changed — say, if a column name was altered in a table the application queries? What does this tell you about why schema design decisions are treated with much greater caution than decisions about what data to insert?

Q3

The update anomaly in the merged faculty-department table becomes dangerous only when a partial update is interrupted. If a system could guarantee that no crash ever occurs mid-update, would the merged design become acceptable? Identify what other problem remains even without the crash scenario, and explain why that problem alone should motivate decomposition.

Q4

The Query Optimizer determines whether to use an index or a full table scan. Consider a table with 10 rows versus the same table with 10 million rows. For each case, reason about which strategy the optimizer would likely prefer, and explain why the correct choice is different at different data scales.

Q5

The Transaction Manager serialises concurrent requests — ensuring only one succeeds when two users attempt the same operation simultaneously. What is the cost of this serialization in terms of system performance? And what would happen to the data if the Transaction Manager did not serialise concurrent writes to the same row?

Q6

SQL is described as "not Turing Complete." In the client-server model, two components work together: a host language (Python, Java) and SQL. Explain why this division of labour is architecturally sensible — why would you want data retrieval to be a separate, declarative language rather than just writing it all in Python?

16. Mental Model Checklist

Before moving to the next section, verify that you can reason through each of these without consulting the notes:

Section-Level Mental Model

This section trains you to think about a DBMS as a system built on deliberate separations. Every major concept here is a boundary: between how data is stored and how it is described (abstraction levels), between structure and content (schema vs instance), between defining and operating (DDL vs DML), between what belongs to one entity versus another (decomposition), and between the user-facing query language and the internal execution machinery (the engine).

These separations are not bureaucratic — each one solves a real failure mode. The abstraction stack prevents low-level storage decisions from destabilising the entire application. The schema/instance distinction allows structure to outlive any particular batch of data. Correct decomposition prevents update anomalies from corrupting the database silently. The engine's three-part structure ensures that storage optimisation, query efficiency, and transactional correctness can each be developed and reasoned about independently.

The mental model to retain: a well-designed DBMS is a system of enforced separations, each of which eliminates a class of failure. When you understand what failure each separation prevents, you understand why the system is built the way it is — and you can reason about what would go wrong if any separation were removed.

  • Three abstraction levels → protects each stakeholder from the complexity above and below their concern
  • Schema / Instance separation → structure outlives content; changes to structure are deliberate and controlled
  • DDL / DML separation → defining a container and operating on its contents are fundamentally different actions
  • Logical / Physical design separation → physical changes do not propagate to break logical structure (Physical Data Independence)
  • Decomposition (Normalization) → one fact, one place; eliminates update anomalies and inconsistency
  • Three-engine architecture → storage, query processing, and transaction management each require specialised, independent subsystems
  • ACID properties → the four-part guarantee that transactions always leave the database in a trustworthy state
